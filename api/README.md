# Mailer API — дизайн и спецификация

> **Статус: ПРОЕКТ (не реализовано).** Этот документ — спецификация и правила
> безопасности для публичного API отправки. Пишется ДО реализации, чтобы строить
> по нему. Текущий код в `api/` — заглушки (см. «Что в коде сейчас» ниже).

Назначение: внешние клиенты по **выданному нами токену** могут **запускать отправку**
писем через наш мейлер. API смотрит в **публичный интернет**. Главная задача —
чтобы через токен **нельзя было ни украсть данные, ни атаковать нас, ни превратить
нас в спам-машину**.

---

## 1. Модель угроз (от чего защищаемся)

При «публичный интернет + запуск отправки» главные риски — НЕ классический взлом, а:

1. **Утёкший/слитый токен → спам через нашу инфраструктуру.** Наши домены, SMTP и
   SES улетают в блеклисты → репутация отправителя умирает. Это опаснее кражи данных.
2. **Открытый релей.** Если клиент управляет содержимым (HTML, тема, From, заголовки),
   через нас шлют фишинг и инжектят SMTP-заголовки.
3. **Кража данных.** Токен не должен давать доступ к чужим данным, PII получателей,
   секретам (пароли SMTP, CF-токены), логам, базам email.
4. **DoS.** Поток запросов выжирает ресурсы процесса/БД.

Два правила, вокруг которых строится защита:
- **Токен всегда ограничен (scope + квоты) и мгновенно отзываем.**
- **Клиент НЕ управляет содержимым письма** — только адрес, ссылку и сервис.

---

## 2. Принципы

- **Least privilege / default-deny.** Нет scope под действие → `403`. Токен видит и
  делает только своё.
- **Клиент задаёт минимум.** Тело запроса — `{ service, email, link }` и, опционально,
  безопасные подставляемые переменные (экранируются). Шаблон, тема, отправитель, SMTP,
  сокращатель — выбирает **система** по своей конфигурации сервиса (тот же пайплайн,
  что у бота). Это убивает открытый релей и инжект заголовков.
- **Админка — только в Telegram.** Выдача/отзыв токенов, настройка SMTP/нод/CF —
  никогда через API.
- **Отзыв и срок.** `active=False` — мгновенно; `expires_at` — авто-истечение.
- **Аудит всего.** Каждый вызов → запись (token id, IP, домен получателя, статус).

---

## 3. Токен

- Генерация: `secrets.token_urlsafe(32)`, префикс `mk_live_…`.
- В БД хранится **только `sha256(token)`** — не сам токен. Показываем токен
  **один раз** при создании; потом — только префикс для идентификации.
- Сверка — `hmac.compare_digest` (constant-time), не `==`/`!=`.

### Поля `ApiToken` (планируемая схема)

| Поле | Назначение |
|---|---|
| `id` | публичный префикс для списка (`mk_live_ab12…`) |
| `token_hash` | sha256 полного токена (поиск по хэшу) |
| `owner` / `label` | кому выдан / метка |
| `scopes` | набор прав, напр. `['send']` |
| `allowed_services` | список разрешённых сервисов (`*` — опасно, по умолчанию явный список) |
| `allowed_link_domains` | на какие домены можно слать ссылки |
| `daily_quota` | писем/сутки (жёсткий потолок) |
| `rate_per_min` | запросов/минуту |
| `ip_whitelist` | опциональный список IP/CIDR |
| `sent_today` / `quota_reset_at` | учёт квоты |
| `active` | мгновенный отзыв |
| `expires_at` | срок действия |
| `created_at` / `last_used_at` | аудит |

> Текущая модель `common/models/api_token.py` хранит токен открытым PK — **переделать**
> на хэш по схеме выше.

---

## 4. Аутентификация

```
Authorization: Bearer mk_live_xxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

Проверка на каждом запросе:
1. Есть `Bearer`-токен → иначе `401`.
2. `sha256(token)` найден, `active=True`, не истёк (`expires_at`) → иначе `403`.
3. IP клиента ∈ `ip_whitelist` (если задан) → иначе `403`.
4. Нужный scope есть у токена → иначе `403`.
5. Квота/рейт не превышены → иначе `429`.

Сравнение хэшей — `hmac.compare_digest`. `last_used_at` обновляется.

## 5. Эндпоинты

### `POST /api/v1/send` — запустить отправку *(scope: `send`)*

**Запрос** (клиент задаёт ТОЛЬКО это; реализовано):
```json
{
  "country":     "PL",
  "service":     "myemail.pl",
  "email":       "user@example.com",
  "link":        "https://target.example/path",
  "price":       "199 zł",
  "predmetname": "iPhone 15",
  "id":          "777",
  "username":    "kesha"
}
```
- `country` + `service` — клиент выбирает из каталога (`GET /api/v1/catalog`); сервис
  также ∈ `allowed_services` токена.
- `price` → плейсхолдер `*PRICE*` в шаблоне, `predmetname` → `*PNAME*` (сырые замены,
  как `MAIL_URL` для ссылки). `*DATE*` — **системный** плейсхолдер: текущая дата
  `ДД.ММ.ГГГГ` **в часовом поясе страны** получателя (`COUNTRY_TZ`, zoneinfo — DST
  учитывается), подставляется автоматически, клиент его НЕ передаёт.
- `id`, `username` — **только в лог/трек** (`SendLog.ext_id`/`ext_username`), в письмо
  НЕ подставляются.

**Правила валидации:**
- `country` ∈ каталог, `service` ∈ каталог[country] и ∈ `allowed_services` токена.
- `email` — валидный формат; (suppression-лист — TODO).
- `link` — схема `http(s)`, домен ∈ `allowed_link_domains` токена.
- Содержимое письма (шаблон/тема/From/SMTP/сокращатель) **берётся системой** по
  конфигурации сервиса/рубрики (рубрика — по домену получателя) — клиент не влияет.

### `GET /api/v1/catalog` — доступные страны и сервисы *(scope: `send`)*
Отдаёт `{countries: {PL: {flag, services:[…]}, …}}` — из чего клиент выбирает
`country`/`service`.

**Ответ** (минимум, без внутренних данных):
```json
{ "id": "snd_ab12cd", "status": "queued" }
```
Статусы: `queued` → (воркер) → `sent` / `failed`. **Никогда** не отдаём: какой SMTP/нода
использованы, чужие логи, секреты.

**Ошибки:** `401` нет токена · `403` нет прав/IP/scope · `422` плохой ввод · `429`
квота/рейт · `503` отправка недоступна.

### `GET /api/logs/*` — *(не включать как есть)*
Текущие `/api/logs/errors|sends` отдали бы **email получателей (PII)** по одному
статичному паролю. Либо выпилить, либо переделать под хэш-токен + отдельный scope
(`logs:read`) с привязкой к данным **своего** владельца и минимумом полей.

## 6. Квоты, рейт-лимит, анти-абуз

- **Rate limit** на токен и на IP (напр. `rate_per_min`) → `429`.
- **Суточная квота** `daily_quota` на токен (жёсткий потолок) → ограничивает ущерб
  от утёкшего токена.
- **Глобальный kill-switch** на весь приём отправки.
- **Suppression-лист** — не слать на отбившиеся адреса/жалобы (бережёт репутацию).
- **Идемпотентность** (опц.): заголовок `Idempotency-Key`, чтобы ретраи не
  дублировали отправку.

---

## 7. Архитектура отправки

Приём **НЕ** шлёт синхронно в HTTP-запросе (иначе запросами выжмут потоки → DoS).

```
клиент → POST /api/v1/send → валидация + квота → ОЧЕРЕДЬ → воркер → общий send-пайплайн
                                                   (троттлинг)   (scope-SMTP, автосмена,
                                                                  шаблон, трек-ссылка, лог)
```

Воркер переиспользует существующий пайплайн отправки (общий с ботом: выбор SMTP по
области/автосмена, шаблон сервиса, короткая ссылка с треком, запись в `SendLog`).
Для этого ядро отправки выносится в сервис-функцию, вызываемую и ботом, и воркером.

---

## 8. Хардненинг инфраструктуры

- uvicorn на `127.0.0.1`, `reload=False`; наружу — **только через Cloudflare/nginx**
  (TLS, лимит размера тела, таймауты — анти-DoS). `/docs` закрыт или под авторизацией.
- CORS залочен (не `*` с кредами).
- БД-пользователь API — гранты только на нужные вьюхи; **без** доступа к таблицам с
  паролями SMTP/CF.
- Строгая валидация (pydantic: типы, длины, лимиты), лимит размера запроса.
- Логи без секретов и без полных адресов (домен/хэш вместо полного email, где можно).

> Текущий `api/main.py` поднимает `0.0.0.0:8080` с `reload=True` — **dev-режим,
> наружу так нельзя.**

## 9. Выдача токенов (админка в Telegram, раздел 🛡 API)

Только владелец бота, только в Telegram:
- **Создать** токен → показать значение **один раз**; задать `owner/label`, `scopes`,
  `allowed_services`, `allowed_link_domains`, `daily_quota`, `rate_per_min`,
  `expires_at`, опц. `ip_whitelist`.
- **Список** токенов (префикс, владелец, использование сегодня, статус).
- **Отозвать** (`active=False`) — мгновенно, запись и история/статистика **сохраняются**
  (рекомендуемый способ «выключить» токен, аудит на месте).
- **Удалить** — полностью убрать запись токена (чистка списка). С подтверждением.
  История отправок (`SendLog`) остаётся, но привязка к токену теряется — в старых
  логах он отображается как «удалённый». Для сохранения истории используй **Отозвать**.
- **Статистика по токену** — см. раздел 9.1.

Через сам API управлять токенами **нельзя** (ни создавать, ни удалять, ни читать чужие).

### 9.1. Статистика отправок по токенам

Каждая отправка через API **помечается токеном**: в `SendLog` добавляется ссылка на
токен (`api_token_id`, ALTER-колонка). По ней считается статистика — отдельно по
каждому токену (в Telegram, аналогично разделам STATS / карточке USERS):

- **Отправок** — успешно / ошибки / всего.
- **Переходов** и **конверсия %** — джойн по трек-id (как в STATS, для личных
  short-доменов).
- **Использование квоты** — сегодня / `daily_quota`, дата сброса.
- **Разбивка по сервисам** — сколько и куда слал этот токен.
- **По дням** — динамика отправок (последние N дней).
- **Последняя активность** — `last_used_at`, последний IP.

Доступно только владельцу в Telegram. Клиенту через API статистика **не отдаётся**
(выбран только scope `send`); при желании позже можно добавить отдельный scope
`stats:read`, строго по данным **своего** токена.

---

## 10. Чего API НЕ делает (явно)

- Не отдаёт секреты (пароли SMTP, CF-токены) и чужие данные.
- Не принимает произвольный HTML/тему/From/заголовки от клиента.
- Не даёт читать чужие логи/статистику/базы email.
- Не управляет токенами, SMTP, нодами, рубриками, настройками.
- Не редиректит на произвольные URL из запроса (резолв только зарегистрированных
  кодов — как уже сделано на нодах).

## 11. План реализации (фазами)

**Фаза 1 — фундамент (без приёма отправки):**
- Переделать `ApiToken` на хэш-схему (раздел 3), ALTER/создание таблицы.
- Раздел 🛡 API в боте: создать / список / отозвать / **удалить** / квоты / сервисы.
- Хардненинг `api/main.py` (localhost, reload off, за CF/nginx).
- Починить/закрыть `/api/logs/*` (хэш-токен + scope или выпилить).

**Фаза 2 — приём отправки + статистика по токенам (СДЕЛАНО, п.46):**
- ✅ `POST /api/v1/send` + `GET /api/v1/catalog`: аутентификация, валидация
  (страна/сервис/email/ссылка), рейт-лимит (in-memory) + суточная квота, очередь
  (`api/worker.py`) + воркер.
- ✅ Общий send-пайплайн вынесен в `bot/services/send_core.py` (`build_payload` +
  `send_payload`), зовётся и ботом (`flow_send`), и воркером.
- ✅ Плейсхолдеры `*PRICE*`/`*PNAME*` в `render_template` (+ `id`/`username` в лог).
- ✅ **Привязка к токену:** `SendLog.api_token_id`/`ext_id`/`ext_username` (ALTER).
- ✅ **Статистика по токену** в Telegram (кнопка 📊 в карточке): отправки/переходы/
  конверсия, квота сегодня, по сервисам и дням.
**Фаза 2.1 — доусиление (СДЕЛАНО, п.47):**
- ✅ **Suppression-лист** (`suppression`): адреса, на которые не слать (отписки/
  жалобы/баунсы). Проверяется в `send_core.build_payload` (бот+API → 422). UI в
  Telegram (🛡 API → 🚫 Suppression: список/добавить/удалить).
- ✅ **Аудит вызовов** (`api_audit`): мидлвара пишет каждый /api/* вызов (токен/IP/
  метод/путь/статус). UI: 🛡 API → 🧾 Аудит (последние 20).
- ✅ **Идемпотентность**: заголовок `Idempotency-Key` (скоуп на токен) — повтор с тем
  же ключом возвращает прежний ответ, без новой отправки (`idem_key`).
- ✅ **Graceful-shutdown воркера**: при остановке API очередь дренится (join с
  таймаутом) — поставленные/выполняемые отправки не теряются.
- ⏳ Осталось: тела `/api/logs/*`; авто-пополнение suppression из SES-нотификаций
  (bounce/complaint); TTL-очистка `idem_key`.
